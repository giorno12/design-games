# Design Games

把创意转成玩家可体验、团队可制作、结果可验证的设计。不要堆砌术语或模板；根据任务规模选择最短但完整的工作路径。

## 基本原则

- 从目标玩家、使用情境和体验目标出发，不从功能清单出发。
- 把“有趣、流畅、史诗、平衡”等形容词改写成可观察行为、规则或指标。
- 同时设计正常路径、失败路径、边界条件、反馈和恢复方式。
- 让机制、关卡、叙事、数值和技术表达同一体验，不分别自洽却互相冲突。
- 区分**事实、假设、设计提案、待验证结论**；不要把偏好说成定律。
- 优先设计玩家决策及其后果，再补内容和包装。
- 把原型与测试当作设计步骤，不把文档完成当作设计完成。
- 不照搬竞品、书籍模型、教学演示参数或引擎默认值；说明适配条件。
- 默认考虑可访问性、本地化、未成年人保护及付费机制的伦理风险；实际发行合规结论需另查目标地区现行规则。

## 标准工作流

### 1. 定义任务与交付

识别用户是在要创意、完整方案、局部规则、文案、计算、诊断、评审还是测试计划。保留用户已给定的平台、类型、受众、视角、操作、商业模式、团队与引擎约束。

信息不足但能合理推进时，列出不超过 5 条关键假设并继续。只有不同答案会根本改变方案且无法推断时，才集中询问最高影响的问题。小任务直接回答，不强制展开完整 GDD。

### 2. 建立设计契约

至少明确：

- **目标玩家与情境**：谁在什么平台、单局时长、社交关系中游玩。
- **体验目标**：希望玩家感受到什么，并表现出什么行为。
- **核心决策**：玩家反复做什么判断，为什么不是显然最优或机械执行。
- **输入与约束**：操作、资源、信息、空间、时间、内容和技术限制。
- **成功证据**：原型观察、测试问题、数据或验收结果怎样证明方向有效。

### 3. 形成机制闭环

用以下链路检查方案，不必机械展示每一步：

**体验意图 → 玩家决策 → 操作/选择 → 状态变化 → 规则结算 → 视听与界面反馈 → 新情境 → 长期后果**

为每个关键规则写明输入、输出、优先级、状态归属、失败条件和边界。涉及资源时同时写来源、去向、存量与异常处理；涉及动作时写启动、持续、取消、打断、结束与恢复。

### 4. 做跨专业接线

检查方案在相关专业间是否对齐：

- 系统是否提供关卡需要的空间、敌人、目标和节奏工具。
- 关卡是否给机制留下可读、可执行、可恢复的场景条件。
- 技术实现是否保留设计语义，是否有数据归属、回退、调试与预算。
- 叙事是否解释并强化玩家正在做的事，而非与玩法奖惩相矛盾。
- 数值是否支持目标决策和体验时长，而非只让表格闭合。
- UI、声音、动画、特效是否让玩家理解因果、风险和结果。

发现冲突时先修最早造成错误的层，不用最后的表现或参数掩盖根因。

### 5. 验证与迭代

为最重要的假设设计最便宜、最能证伪它的测试。优先测试核心决策，再测试内容量和包装。每次测试只改变少数可解释变量，记录版本、输入、观察、结论和下一步。

数值计算优先使用 [design_math.py](scripts/design_math.py)；模型不能替代玩家测试。技术方案必须包含可复现输入、调试信息、性能或容量预算、回退和验收用例。

## 输出契约

### 快速设计或咨询

按需要给出：**结论 → 核心规则 → 设计理由 → 主要风险 → 最小验证**。不要附加无关章节。

### 完整方案

按任务选用：设计契约、体验支柱、核心循环、详细规则、内容与反馈、异常和边界、跨专业依赖、数值或性能预算、埋点/调试、验收用例、迭代计划。具体结构从 templates.md 选择，不重复输出所有模板。

### 设计诊断或评审

按严重度列出问题，每项包含：**证据/复现 → 根因 → 玩家影响 → 最小修正 → 验证方法**。区分确定性错误与风格偏好；用户只要求诊断时不要擅自重写整个方案。

### 文案任务

先给可直接进入游戏的文本，再按需附变量、触发、条件、角色语气和本地化说明。不要只给创作建议而省略正文。

### 数值任务

写清单位、公式、假设、有效范围和示例；给出基准、目标区间、敏感性及失衡信号。离散事件与连续近似分开，期望与最坏情况分开。

## 最终质量门

交付前逐项自检，只报告仍存在的真实缺口：

- 核心循环是否闭合，玩家是否能理解“我做了什么、为何得到这个结果”。
- 是否至少存在有意义的选择、技巧、表达、发现或掌握空间，而非只有奖励刺激。
- 状态优先级、打断、取消、失败、恢复、重复触发和极端输入是否有答案。
- 资源是否有来源与去向，数值是否有单位和边界，随机机制是否说明概率语义。
- 关卡是否有读图、引导、节奏、Checkpoint 和失败恢复。
- 技术是否有所有权、时序、空间/单位、预算、回退、调试和验收。
- 文案是否符合角色、情境、玩法状态及文本长度/变量约束。
- 是否指出最高风险假设及下一步最便宜的验证。
